# SHIP-V1-002 implementation handoff

## Summary

Store multiple GRD POs per shipment, optional SO/Product lists and a reviewed source-data backfill. Warehouse shipments retain PO# 0 and their SO separately. Work is on `feature/SHIP-V1-002-shipment-order-details`; production is unchanged.

## Changes Made

- Added a reversible migration for SO/Product arrays, shared PO references and shipment links. All new foreign keys explicitly use ON DELETE NO ACTION in SQL and TypeORM. Existing PO strings, audit fields and soft-deleted records are preserved.
- All list/detail/search/dashboard responses include structured lists. Existing PO# remains a display summary and legacy single-reference input. Structured edits preserve reference identity, including commas inside an opaque legacy identifier.
- Existing TypeORM, PostgreSQL and Zod handle persistence and validation. No production dependency or lockfile change. Mapping and matching remain explicit business rules; no custom CSV parser or replacement ORM/validation framework was introduced.
- Added an operator backfill CLI that defaults to READ ONLY, validates the source SHA-256, refuses populated/stale targets, locks exact records, applies atomically and re-reads persisted values. It is never invoked by migration or startup.
- Prepared a private source plan for 37 shipments / 185 business-field changes (39 PO references, 39 SO values, 47 products). Eight unresolved shipments remain excluded. Plans and source CSV remain Git-ignored and outside the Docker build context.

## Review Notes

Review the migration before deploying. Rollback drops new SO/Product data and refuses a PO-summary truncation; back up and review before a production rollback. API/migration deployment must precede frontend list edits.

Customer/Vendor remain the existing shipment-wide fields. Matching CSV line items must agree on these values; conflicting or uncorroborated matches are excluded rather than guessed. Product/SO lists are shipment metadata; this change does not attribute individual quantities or products to particular POs.

`purchase_orders` is a reference ledger without customer/vendor ownership or an order-management API; 0 is a reserved warehouse marker. Associations and PO display summaries are maintained in the owning transaction. Shared-reference inserts use consistent ordering for batches. Legacy `poNumber` is one opaque reference, not a string to split.

Backfill updates edit timestamps/system attribution and lock versions, preserves monitoring/notes/snapshot pointers and next-check scheduling, and rejects reapplication as stale. Recheck production after the new migration before approving the live operation.
